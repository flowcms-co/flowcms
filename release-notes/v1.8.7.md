# v1.8.7: removing a field no longer moves its data into the next one

Removing a field from a content type or component could be mistaken
for a rename. When a field was taken out of the schema, the code that
carries entry data across renamed fields matched the removed field to
its neighbour by position and type, and wrote the removed field's
value into that neighbour on every entry of the type. A URL field
removed from a city page type ended up in the hero headline of all its
pages.

A field is now matched by its id and nothing else. An id that is gone
from the new schema means the field was removed: its data is left in
place on each entry and nothing is written into any other field. A
genuine rename, where the id stays and the name changes, still carries
the data to the new name. Position matching remains only for fields
from older imports that never had an id, and only against another
id-less field of the same type.

Saving a schema never creates drafts or adds keys to entries. If you
saw drafts appear after a schema change, they came from a later save of
those entries.

## Notes

No migrations, no config changes, no new environment variables. API
only.
