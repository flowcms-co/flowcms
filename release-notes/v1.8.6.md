# v1.8.6: content that stays put, slugs that build themselves

## A component field no longer loses its content on save

A component field set up as a single block could hold a list of blocks
if the content was written through the API. The editor showed one
empty block for it, and saving the page wrote that empty block over
the list. Four live pages lost their body this way before it was
noticed.

Three things changed:

- The editor shows what is stored. A list under a single field appears
  as a list you can edit, with a note saying the field and the content
  disagree.
- Saving cannot wipe it. If the editor sends an empty block where a
  list is stored (or an empty list where a block is stored), the stored
  content is kept. A real edit still goes through.
- Switching a component field between single and repeatable in the
  Schema Builder now converts existing entries: a block becomes a
  one-item list, a list becomes its first block. When blocks are
  dropped that way the change reports which entries were affected; the
  dropped blocks stay in each entry's version history.

## Slug patterns per content type

A content type can now define how its entries' slugs are built, under
Slug pattern in the Schema Builder, for example
{service.slug}-{city.slug} or {title}. When set, the slug is built on
create and on every save, kept unique within the type, and shown
read-only in the editor with the pattern beside it. Editors never type
it.

The same placeholders work in the type's URL pattern and preview URL,
so a page can live at /{service.slug}/{city.slug} and preview there.
{field} takes a field of the entry; {ref.slug} and {ref.title} take the
slug or title of the entry a Reference field points at. The URL
pattern is now available on every content type, not only reference
types.

Existing entries keep their slugs until they are next saved. A slug
only appears once every placeholder has a value.

## Bulk publish handles pending drafts

Bulk publishing live entries that had unapproved draft changes queued
a job that reported success while nothing was published. Someone with
publish rights now approves and publishes those drafts in bulk, the
same as Approve then Publish on each one. Entries that cannot be
published are listed as failed, with the reason and the field at
fault, not counted as done.

## Preview URL and the live-edit bridge

- A preview URL set on a content type is now used first, with the
  workspace URL as the fallback, and a template keeps its query string
  (…/{slug}?cms=edit).
- The live-edit script learns the studio's address from the studio's
  first message rather than from the page that linked to it, so a site
  that reloads itself inside the preview keeps working. No more
  noreferrer workaround.

## Quality, Plagiarism, Refresh and Quick Suggestions see everything

These screens looked at the newest 500 pages (Content Quality: 100).
Content Quality and Plagiarism now cover every published page up to
5,000, loading in batches with a progress line and saying so when a
workspace has more. Refresh lists every published page. Quick
Suggestions keeps sampling 40 pages, and now fetches only those.

Duplicate detection across pages was rebuilt to index phrases once, so
3,000 pages scan in about 3 seconds instead of freezing the screen. A
phrase that appears on more than 50 pages is treated as the site's
standard text, not a copied passage.

## Notes

No migrations, no config changes, no new environment variables. API
and studio.
