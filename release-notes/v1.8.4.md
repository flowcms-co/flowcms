# v1.8.4: see and edit every entry, however many there are

The content list showed only the 500 most recently updated entries. A
workspace with more than that, such as one with a page per city, could
not browse to the rest. Search had the same limit: it looked through
those 500 only, so an older entry could not be found at all.

The list now reads from the database one page at a time, and search,
filters and sorting run over every entry. Tested with 50,000 entries:
any page opens in about a tenth of a second.

## What this changes

- Content list: every entry is there, 15 to a page. Search by title or
  slug, the type, status, author and language filters, and sorting all
  cover the whole workspace.
- The counts above the list, and the list of authors to filter by,
  count everything.
- Global search finds any entry.
- Reference fields, such as choosing a city for a page, search all
  entries of that type as you type, instead of offering the first 500.
- Calendar: loads the month on screen. A month with more than 500
  items shows the first 500 by date and says how many there are.
- Publish queue: shows everything that is not live yet.

## Good to know

- Select all now selects the rows on the current page.
- Sorting by SEO score or by views is the slowest thing the list does,
  about half a second at 50,000 entries.
- The Content Quality, Plagiarism, Refresh and Quick Suggestions
  screens still look at the 500 most recent entries.

## Notes

One migration, applied automatically on boot. It adds a title column
that the database keeps in step with each entry, and an index for the
list's default order. On 50,000 entries it takes about a second. No
config changes, no new environment variables. API and studio.
