# v1.9.3: audit fetch prefix, and a crawl rate that learns the site's limit

## Audit fetch prefix

Some hosts can only scope a rate limit by URL path, not by client, so a
site on such a host cannot give the crawler a higher limit by user
agent. What it can do is serve the same pages under a keyed path that
is exempt from the visitor limit:

    https://example.com/_audit/<key>/<page path>   serves   <page path>

Settings, Workspace, System has a new optional **Audit fetch prefix**.
When it is set, the page audit, the site crawler and the background
re-check request `site URL + prefix + page path`.

- The prefix is a secret. It is stored encrypted, never shown again
  (the field shows only a masked form), never returned by the API, and
  never appears in findings, issue rows, "View live" links, exports,
  notifications, job records or logs. Everything is stored and reported
  under the real page URL.
- PageSpeed, `robots.txt`, `sitemap.xml` and `llms.txt` are fetched as
  before, without it.
- **Test** fetches the homepage directly and through the prefix and
  reports both status codes and whether the titles match, with a clear
  message for 404 (wrong key, or the prefix is not set up on the site)
  and 403 (blocked).
- Stored page facts, conditional requests and the unchanged-page skip
  are keyed on the real URL, so turning the prefix on or off does not
  cause a re-crawl.
- If the site stops accepting the prefix, the run stops with "Audit
  fetch prefix is no longer accepted by the site" and every page keeps
  its last good result.

## Crawl rate

On a site allowing 120 requests a minute, "Re-check every page" fetched
84 pages in 22 seconds, then stalled for over ten minutes, reported 12
failed pages, and took minutes to cancel. The rate climbed too fast for
a per-minute limit, and every refused request lengthened the pause.

- The rate climbs much more slowly: 10% after every 30 healthy
  responses, and only after a full minute without a refusal.
- The first refusal teaches it the limit. It sets a ceiling at 70% of
  the rate that was refused and never goes above it again. The ceiling
  is remembered per workspace and host, so later runs start below it.
  Changing the maximum rate or the audit fetch prefix clears it.
- Refusals within ten seconds of each other are one event: one halving
  and one wait, however many requests were in flight.
- With no Retry-After, it waits one minute, not a growing pause.
- While it waits, the job and the Optimizer say "Waiting, the site
  asked us to slow down (resumes in Ns)".
- Pause and cancel take effect within a second, also during a wait.
- Pages refused by the rate limit are retried and are no longer counted
  as failed.

## Home dashboard

The "SEO issues" tile shows "Audit in progress, N of M" while an audit
runs, like the Optimizer.

## Notes

One migration, applied automatically on boot:
20261007090000_seo_fetch_prefix (Workspace.seoFetchPrefixEnc and
seoLearnedRate). No new environment variables; the prefix is encrypted
with the existing SECRETS_ENCRYPTION_KEY.

API changes: PATCH /workspace accepts `seoFetchPrefix` (write-only; an
empty string clears it) and GET /workspace returns `seoFetchPrefixSet`
and `seoFetchPrefixMasked`. New route: POST /seo/fetch-prefix/test.
GET /seo/scan/issues `run` adds `waitingUntil`.

Known limits: the learned ceiling is kept per API process during a run
and stored per workspace between runs. The crawler follows at most
three redirects per page.
