# v1.8.5: select everything, and bulk actions that never hold up the app

## Select all means all

Since v1.8.4 the content list shows every entry, a page at a time, and
Select all picked only the rows on screen. It now picks every entry the
list is showing, across all pages.

A line above the table gives you the choice:

- All: every entry that matches your current search and filters. The
  checkbox in the table header does the same.
- This page: only the rows on screen, added to what is already
  selected.
- Clear: nothing.

It also shows how many are selected, for example "11 of 1,337
selected". Search first, then select all, to act on just the entries
you searched for.

## Schedule and Duplicate run in the background

Publish, Move to draft and Delete already ran as background jobs.
Schedule and Duplicate did not: the browser sent one request per
entry, which only worked for small selections. Both are now background
jobs, so every bulk action takes any number of entries while the app
stays usable.

Tested with 3,000 entries scheduled and 1,000 duplicated in one go.
Each job started at once, and the content list kept loading in under a
twentieth of a second while it ran. Expect roughly 100 entries a
second, so about a minute and a half for 10,000.

A job that cannot process some entries still finishes, and lists which
ones failed and why. Scheduling a single row from its menu is still
done directly, so a problem with that entry shows straight away.

## Good to know

- Delete with everything selected deletes everything. The confirmation
  shows the real count.
- Bulk jobs run one after another, so a second large job waits for the
  first.

## Notes

No migrations, no config changes, no new environment variables. API
and studio.
