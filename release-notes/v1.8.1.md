# v1.8.1: choose the author, SEO fields that stay put, safer rollbacks

## Choose who the author is

An entry's author used to be whoever created it, forever, even when
someone else rewrote it later. There are now two ways to change that.

A workspace setting, under Settings, System, Workspace, decides who is
shown as the author of every entry:

- Original creator: the person who created the entry. This is the
  default, so nothing changes until you switch it.
- Latest editor: the last person who changed the content. Approving or
  publishing someone else's work does not make you the author, and
  neither does a save that changes nothing.

You can also pick the author by hand on any entry. The Review tab in
the editor has an Author field: choose any team member, or Automatic
to follow the workspace setting again.

The content list, the publish queue, the calendar and the author filter
all follow the chosen author. Existing entries are filled in from their
version history during the update, so Latest editor works for content
written before this release. The original creator is always kept, so
switching back loses nothing.

Dashboard figures and the "your content was approved" style
notifications still go by the original creator.

## SEO and Schema fields no longer come up blank

The SEO tab in the editor's side panel could show an empty meta
description and focus keyword for an entry that had both saved. The
panel read its fields before the entry had finished loading and never
looked again. The values were saved; they just were not shown.

The same panel had a second problem: after Save SEO, the editor kept
its older copy of those fields, so switching tabs showed them blank
again and the next save of the page could write the old values back
over the new ones.

Both are fixed for the SEO tab and the Schema tab. The panel also says
"Could not save" when a save fails, instead of always saying "Saved".

If your fields showed blank before this update, open the entry after
updating. Values that were saved will appear. If they are still empty,
they were overwritten by the second problem and need entering once
more.

## Safer rollback after a failed update

When an update failed and the previous version also did not come back
healthy, the updater restored the pre-update backup, and that restore
cleared the media folder before unpacking the backup's copy. An update
never changes media, so there was nothing to put back, and a full disk
or a damaged archive at that moment could leave the media folder empty.

The rollback now restores the database only and leaves media alone. A
manual restore from Settings still replaces media, but it checks that
the backup's media archive is readable before removing anything.

This ships in the updater, which updates itself at the end of a
successful update, so it protects every update after this one.
